# Markdown (documents and generated evidence)

## What it is

Markdown is a way to write formatted text in a plain text file. A line starting with `#` is a heading, `- ` starts a bullet, `|` draws a table,
backticks mark code, and a fenced block marked `mermaid` is drawn as a diagram (see `mermaid.md`).

## Why this repository uses it

The repository explains itself in documents next to the code, and its evidence pack is partly Markdown: the index an assessor reads first, the
scope reports, and the notes on what the provider answers for and what stays with the merchant.

## Where it appears

| File | What it does with this technology |
| --- | --- |
| `README.md`, `ARCHITECTURE.md`, `CHANGELOG.md` | The documents. |
| `docs/adr/0001` to `0003`, `docs/responsibilities.md`, `docs/provider-attestation.md` | Decisions and responsibilities. |
| `evidence/INDEX.md`, `scope-*.md`, `responsibilities.md` | Generated or copied into the pack. |
| `tech/*.md` | These notes. |

## How it works underneath

Markdown is not a program; a viewer turns it into HTML. The generated files are written by Python as plain text with Markdown markers, so they are
readable in a terminal too.

## Walkthrough of this repository's use

`evidence/INDEX.md`:

```markdown
# Evidence pack index

Pack date: 2026-10-27T01:24:50Z. Every file was produced by `make run` (`pci-scope demo`); `manifest.json` records its hash, so a hand edit fails `make verify`.

| File | Requirement | Proves | Date |
| --- | --- | --- | --- |
| payment.har | P1 | the captured browser traffic: no request to the merchant carries a card field or number, and the card fields went to the provider | 2026-10-27 |
| payment-summary.txt | P1 | the same capture, one line per request with where it went | 2026-10-27 |
| proof-after.txt | P1 | a scan of the merchant's log, database and backups for card numbers and card fields, and the lesson's grep commands, all empty | 2026-10-27 |
```

The index is generated by `make run`. The table lists every evidence file with the requirement it supports, what it proves and its date. `make verify`
checks that every file is in it and that its hash matches the manifest.

`docs/adr/0001-a-local-stand-in-for-the-provider.md`:

```markdown
# 1. A local stand-in for the payment provider

Status: accepted, 2026-10-27

## Context

The lesson uses a provider's hosted fields in test mode. That needs an account, keys and a network, and a repository that cannot run without them cannot be verified offline or in a fresh clone.

## Decision

Implement the provider's side locally, with the same shape as a typical payment-intents API: customers, payment intents with a client secret, payment methods created from the browser with a publishable key, confirm, off-session charges, refunds and signed webhooks, plus a hosted card form served from the provider's origin. The merchant's `HttpProvider` speaks only that API, configured by `PROVIDER_BASE_URL` and test keys; settings refuse live keys.
```

A decision record: a title, a status, then the context, the decision and the consequences, so a reader finds the reasoning in a fixed place.

## Mistakes people make

- **Editing generated files by hand.** A hand edit of an evidence file fails `make verify` (hash mismatch).
- **Skipping the blank line** before a list or table.
- **Pasting Python fragments** into Markdown code blocks where ruff 0.17 will try to format them; `tech/` is excluded in `pyproject.toml`.

## Check yourself

1. What marks a heading?
   **Answer:** One or more `#` at the start of a line.
2. Which evidence files are Markdown?
   **Answer:** `INDEX.md`, `scope-before.md`, `scope-after.md`, `scope-change.md`, `responsibilities.md`, `provider-attestation.md`.
3. Why not edit `INDEX.md` by hand?
   **Answer:** It is generated and hashed; a hand edit fails verification.
4. What does a `mermaid` fenced block do?
   **Answer:** A viewer draws it as a diagram.
5. Is Markdown executed?
   **Answer:** No.
